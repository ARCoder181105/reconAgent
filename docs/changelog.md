- **2026-09-04 — fix(services) — segregation rejection now 403** — Refined the self-approval block in `exception_service.approve()` to return **HTTP 403** instead of 409. Rationale: 409 is for a *state* conflict ("nothing pending approval" — the exception isn't in `pending_approval`); self-approval is an *authorization* failure — the state is fine, this specific requester isn't allowed to act — so 403 is semantically correct, and it lets the frontend distinguish "someone already resolved this, refresh" (409) from "you can't approve your own proposal" (403). Test `test_checker_cannot_approve_own_proposal_segregation_of_duties` now also asserts the detail message contains "cannot approve their own proposal", not just the code.
- **2026-09-04 — fix(services) — Maker-Checker segregation of duties** — `exception_service.approve()` now rejects a Checker who is the same person as the Maker who proposed the pending resolution (HTTP 409, "checker cannot approve/reject their own maker proposal"). Previously a single identity could call `/resolve` as maker then `/approve` as checker on their own proposal and it would go through, defeating the whole point of the two-role governance. Adds `_pending_maker_id()` (reads the most recent `MAKER_PROPOSED` event from the append-only log) and a new integration test. Suite 68 passing.
- **2026-09-04 — fix(data) — settlement dates were year 0055/0056** — `generate_settlements._day_to_iso` used `date.fromordinal(base_day)` with a base of `rng.randint(20000, 20800)`, but `fromordinal` counts from year 1 (2024-01-01 ≈ ordinal 738,xxx), so every generated `settlement_date` was **0054–0056** (e.g. `0056-03-13`) — a corrupted year masquerading as ISO. Re-anchored the base to a real ~2024–2026 window (`date(2024,1,1).toordinal() + randint(0,800)`). Random stream is unchanged (still one `rng.randint` call), so all IDs/amounts/UTRs are identical; only dates move to real years. Verified: seed-42 still **48/48, precision/recall/F1/penalized 1.0**, dates now 2025-10-16… The stale generated CSVs/answer_key were regenerated.
- **2026-09-04 — fix(web) — candidates render `→ —`, not phantom scores** — The exception candidates stored by the engine **never** carry a per-candidate `score` or `line_id` (audited 76 stored rows: 0 have either); they are settlement hints with amount + date, or a bare settlement id. The Maker-queue row rendered `{settlement_id} → {line_id ?? "—"}` and a `score%`/`—` tag that were modeling a scored ranking that doesn't exist, so every row showed the inconsistent `→ —`. Simplified to render `settlement_id` plus an evidence tag that always shows the real `₹amount · date` (or nothing when the engine had only a bare id); `Candidate.score/stage/line_id` kept optional for future ranking merge.
- **2026-09-04 — fix(services) — LLM queue survives bad/missing GEMINI_API_KEY** — `TiebreakQueue._drain()` constructed the genai client (`self._gen_factory(self.api_key)`) **outside** the try/except, before the task loop. With a missing/invalid `GEMINI_API_KEY` (the default in `.env.example`) the client factory raised and the whole background thread died immediately — queued exceptions stranded forever with no event, no fallback, and zero indication anything was wrong; this contradicted the module's own guarantee that LLM failure degrades to a deterministic fallback. Now the client is built **lazily inside** the loop's try, so a construction failure persists the deterministic `fallback_decision()` (a reviewable `AI_TIEBREAK_SUGGESTED` event with `source=fallback`) and marks the task failed instead of killing the worker. New test `test_client_construction_failure_persists_fallback_not_stranded`. Suite 68 passing.
